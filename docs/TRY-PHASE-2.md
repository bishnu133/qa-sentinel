Steps 1–6 and 9 need **no AI** and cost nothing. Steps 7–8 run the AI (small, capped). Step 10 needs a real Jira.
Do 1–6 first; they cover most of phase 2.

## 5. Budgets stop AI work (no AI: it stops before any call)

```bash
python3 - <<'PY'
import json
f='.qa-sentinel/stories/SHOP-101.json'
d=json.load(open(f)); d['totalCostUsd']=24.95; json.dump(d,open(f,'w'),indent=2)
PY
qa-sentinel spec --story-file ../stories/SHOP-101.md; echo "exit $?"
qa-sentinel stories --stories-dir ../stories --story SHOP-101
```
Expect: `✗ AI budget: this story has used $24.95 of its $25 (automation.budgets.perStoryUsd)…`, **exit 4**; `stories` shows the same under "not started". Now prove `--force` does not bypass it:
```bash
qa-sentinel spec --story-file ../stories/SHOP-101.md --force; echo "exit $?"      # still exit 4
```
Reset: set `totalCostUsd` back to 0 in the file (or delete `.qa-sentinel/stories/SHOP-101.json`).
Optional: in `qa-sentinel.config.yaml` add `automation: { budgets: { perStoryUsd: 0.05 } }` and see the message name that setting; remove it afterwards.

## 6. Known defects fixed: marker removal (no AI)

```bash
mkdir -p tests/api/demo test-results
cat > tests/api/demo/defects.spec.ts <<'TS'
import { test, expect } from "@playwright/test";

// QA-BUG: https://jira.example.com/browse/SHOP-900
// QA-AGENT: expected 409 but the API returned 201
test.fail("rejects a fourth order @story:SHOP-101 @ac:AC-1", async () => {
  expect(1).toBe(1);
});
TS
# A real run: the bug is "fixed" (the test passes), so Playwright reports "Expected to fail, but passed".
# (Not "> test-results/results.json": Playwright empties test-results/ when it starts and the file is lost.)
PLAYWRIGHT_JSON_OUTPUT_NAME=test-results/results.json npx playwright test tests/api/demo/defects.spec.ts --reporter=json || true
ls test-results/results.json               # must exist
git add -A tests && git commit -qm "demo defect"
qa-sentinel known-defects                  # report only
git diff --stat                            # nothing changed yet
qa-sentinel known-defects --apply --commit
git log -1 --format=%B                     # contains "Generated by qa-sentinel known-defects"
git show HEAD | grep '^[-+]'
```
Expect: report says 1 FIXED; the commit (on branch `qa-sentinel/defect-fixed-<date>`) turns `test.fail` into `test` and removes the two comment lines, nothing else. Try the opposite: change `"status":"unexpected"` to `"expected"` and the error part to `[{"status":"passed"}]` in the JSON, run `known-defects` → "still failing (as expected)", nothing to edit.
Go back: `git checkout -` (back to your branch).

## 11. Jira settings: bug to story, ready statuses, components (read-only)

Keep your Jira URL, email and token out of git (use environment variables; do not paste them anywhere). In `qa-sentinel.config.yaml` set, for example:
```yaml
requirements:
  jira:
    featureIssueTypes: [Story]          # use the types your Jira really has
    workflow: { readyStatuses: ["Ready for Testing"] }
    hierarchy: { links: [{ name: "is caused by", from: [Bug] }] }
    components: { YourComponent: your-service }
```
```bash
qa-sentinel doctor --online
qa-sentinel story-check --story YOUR-BUG-KEY
qa-sentinel stories --story YOUR-BUG-KEY
```
Expect: `doctor` says OK or warns about a status, issue type or link name Jira does not have (with the names it does have); `story-check` ends with "Which feature this card belongs to" and says how the bug reaches its story, or why it does not; `stories` lists the story, not the bug. If a bug is not attached, the sentence says why.

## 12. Phase 3 checks (no AI; read-only)

Per-AC readiness (needs a story with an `expected/<KEY>.md` whose ACs list `Services`, and `workspace.services[].version` set):
```bash
qa-sentinel feature YOUR-KEY --env uat
```
Expect a table "Ready for end-to-end tests, per acceptance criterion". An AC that lists only a deployed service shows ✅ even if another service of the story is still waiting.

Draft gap report (in an MR pipeline, or simulate):
```bash
CI_MERGE_REQUEST_IID=1 CI_PROJECT_ID=1 CI_MERGE_REQUEST_TITLE="Draft: test" qa-sentinel gap-report -s <service>
```
Expect "merge request is a draft; the gap report waits" and exit code 0. Without a GitLab token it uses the title; with one it asks GitLab.

Refresh behaviour (needs a real MR with a GitLab token and AI access): mark the MR ready and let the pipeline post the report. Push a docs-only change: expect "nothing changed since the report for …" and the MR comment untouched. Push a code change: the same comment is updated and starts with "Updated for commit …".

## 13. One QA status comment (writes a comment on a Jira story)

Use a test story you own; this adds one comment to it. Needs Jira access with comment permission and `reporting.jira.baseUrl`/`requirements.jira.baseUrl` set.
```bash
qa-sentinel feature YOUR-KEY --post        # adds the "QA status" comment with a feature section
qa-sentinel feature YOUR-KEY --post        # run again: the same comment is edited, no second comment
```
Expect one comment titled "QA status · YOUR-KEY", with "Updated … UTC" under the section. If you also run `gap-report --post` for the story (a dev MR), its section is added to the same comment.
